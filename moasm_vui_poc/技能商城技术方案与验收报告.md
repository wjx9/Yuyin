## 执行摘要

**结论**：技能商城 POC 已完整跑通并通过全部验收（P1–P4.4），**365 个自动化用例全绿**。方案采用「官方 MCP 目录」模式——加一个新 MCP = 开发写一个 `connectors/*.json` → 管理员只点"上架" → 用户手机端启用时填 API Key → 语音助手 ≤30s 生效，从根上解决了"技能写死、无法热插拔"的问题。

**依据**：
- 预置 weather / stock / region / mcdonalds / eastmoney **5 个官方连接器**，覆盖 none 与 byok 两种凭证形态；
- 内置能力（闲聊/闹钟/高德全家桶/新闻/出行/快递/音乐等 **22 个 intent**）同步进入同一商店目录，`transport=local` 由 `LocalHandlerClient` 转回原 Handler；
- 动态凭证按 `credentials.schema` 动态渲染表单，AES-256-GCM 加密存储，新 MCP 零端上改动；
- 版本号机制 + 30s TTL 实现按用户热插拔，停用保留选购、退订才移除；
- 自动化测试：服务端 **304** + 商店 **42** + 手机端 **19** 全绿，flutter analyze 无告警。

**约束**：槽位类型仅 string/integer；每用户×每技能一个常驻连接（商用需收敛连接池，LRU 上限 200 用户图）；platform 托管凭证与 OAuth 未落地；多工具 MCP（如麦当劳 30 个工具）当前固定调 entry_tool。

**行动**：当前可用于演示与验收；商用前优先补齐连接池、真实账号体系（OAuth）、platform 凭证托管与多工具路由。

> 本方案只覆盖 MCP 类型技能（云端沙箱类 skills 因商用沙箱非技术障碍，本轮不纳入）。所有架构事实与数字均来自仓库源码与自动化测试结果。

## 一、项目定位与目标

把"出行 / 快递 / 地图 / 新闻 / 音乐 / 闲聊 / 天气 / 点餐…"多个第三方能力，用一层 Gemini 意图分流编排成单一语音对话入口。此前 demo 中所有技能是写死的；本方案引入技能商城，让真实用户能"热插拔"选购若干技能，三方可上架、用户可自选、语音助手直接可用。

**最新模型（官方 MCP 目录模式）三方职责**：

| 角色 | 职责 | 不做什么 |
|---|---|---|
| **开发** | 把新 MCP 写成 `connectors/*.json` 目录文件（评审后入库） | 不管运行期上架/下架 |
| **管理员** | 管理后台把目录技能上架/下架；自定义 MCP 的新增/删除（逃生通道） | 不再从零组装 MCP |
| **用户** | 手机端选购 → 启用 → 自动弹凭证表单填 API Key → 语音用起来 | 不接触 manifest |

**三种技能来源统一目录**：

| 来源 | publisher | 接入方式 | 谁维护 |
|---|---|---|---|
| 官方 MCP 目录 | `catalog` | `connectors/*.json` 声明式，启动幂等同步 | 开发写 JSON，管理员只上架/下架 |
| 内置能力 | `builtin` | 商店端 `builtin_catalog.py` 轻量快照 + 主服务 `mcp_skill/builtin.py` 实际注册同步 | 代码自动同步 |
| 自定义 MCP | `poc`等 | 管理后台 probe 发现 → 手拼 manifest 发布（逃生通道） | 管理员 |

> 来源：仓库《最终技术路线.md》§1 + §5.1｜口径：2026-08-28 官方目录模式

## 二、总体架构与端到端链路

系统由 4 个部署单元 + 1 个共享层组成：技能商城（FastAPI :9000）承载目录/选购/启停/凭证/上架；服务端（server_py :8000）做 Gemini 意图分流并按用户装配；手机端（Flutter）提供语音与技能商店页；MCP Server 提供能力；ui_py 为共享呈现层。

**部署单元一览**：

| 部署单元 | 端口 | 入口 | 角色 |
|---|---|---|---|
| 服务端（大脑） | 8000 | `server_py/serve.py` | Gemini 意图分流 + 语音 `/chat` |
| 技能商城 | 9000 | `skill_store/main.py` | 目录 / 选购 / 启停 / 凭证 / 上架下架 |
| mock MCP | 9100 | `mcp_skill/mock_server.py` | 本地演示 MCP（可 `--require-auth`） |
| 手机 App | — | `client_flutter/` | VUI 语音 + 技能商店页 |

**端到端数据流**：

```
用户说话「贵州茅台今天最新价」
  → POST /chat {query, user_id, session_id, platform:mobile}
  → ChatService._assistant_for(user_id)     # store sync 版本命中 → 复用缓存图
  → AssistantGraph.run()
       analyze → decide → execute_batch
            → Dispatcher.execute(intent="eastmoney_mcp")
            → MCPHandler.handle(query, ctx)
            → McpToolClient.call_tool("mx_ashare_finance_data", args, timeout=30)
               （凭证由 SkillCredentialProvider 现取明文，注入 header em_api_key）
            → MCP Server 返回 → RouteResult(text, status=success)
       compose → Gemini 组织最终答复
  → POST /chat 200 {"text":"…","intent":"eastmoney_mcp",…}
```

**热插拔生效时序（≤30s）**：

```
用户在手机端启用/停用/配凭证
  → 商店 version+1（同事务）
  → 服务端 SkillRegistry 缓存 TTL 30s 到期后重新 GET /me/skills/sync
  → 版本变化 → ChatService 只重建该用户 graph（关闭旧 MCP 连接防线程泄漏）
  → 下一次请求即走新路由
```

> 来源：仓库《最终技术路线.md》§2 + §3｜口径：端口与入口以仓库为准

## 四、核心数据模型（4 张表）

| 表 | 作用 | 关键字段 |
|---|---|---|
| `skills` | 技能目录 | `skill_id` PK、`manifest`(完整 JSON)、`publisher`(`catalog`/`builtin`/自定义)、`status`(active/inactive) |
| `user_skills` | 用户选购关系 | `(user_id, skill_id)` PK、`enabled`(1 启用/0 停用，由迁移函数幂等添加，旧行默认 1) |
| `user_skill_versions` | 每用户版本号 | `user_id` PK、`version`（独立表，避免并发同秒撞值） |
| `user_skill_credentials` | 用户凭证 | `(user_id, skill_id)` PK、`cred_json`(AES-256-GCM 密文)、`updated_at` |

**建表 SCHEMA 要点**：
- `user_skills.enabled` 列**不在建表 SCHEMA 中**，由 `db.py::_migrate_user_skills_enabled()` 迁移函数幂等添加（旧库缺列则 ALTER ADD，既有行默认 enabled=1）；
- `user_skill_credentials` 密文列名为 `cred_json`（非 `encrypted`）；
- `version` 用独立表而非 `MAX(updated_at)`：并发/同秒写入会撞值，无法可靠判变更。

## 六、核心机制

### 6.1 官方目录模式（catalog + builtin 双目录同步）

**connector catalog（官方 MCP 目录）**：
`skill_store/connectors/*.json` 声明式目录，每个文件 = 一份完整 manifest + 可选 `default_status`。商店启动（lifespan）自动执行 `catalog.sync_catalog()`，管理员也可点「重新同步目录」（`POST /skills/sync-all`）免重启。

同步语义（幂等，放心反复操作）：
- 新 connector 落库取 `default_status`（缺省 `inactive` = 待上架，不会悄悄上线）；
- 已有行的 `status` 不被触碰（保留管理员当前上架/下架）；
- 仅 manifest 或 publisher 变化才写库；仅 manifest 变化才 bump 持有者（≤30s 重建图）；
- `publisher='catalog'` 标记目录技能，管理后台中 catalog/builtin 技能**不显示删除按钮**。

**builtin catalog（内置能力目录）**：
内置能力（闲聊/闹钟/高德全家桶/新闻/出行/快递/音乐等 22 个 intent）也进入同一商店目录，保证直接访问商店（:9000）和通过主服务代理（:8000/skill-store）看到的内置能力一致。两条同步路径互补：
1. **商店端轻量快照**（`skill_store/builtin_catalog.py`）：商店启动时自动跑，不依赖 Dispatcher/Gemini，按 env key 是否配置决定 active/inactive（缺 key 的能力标 inactive，不虚假展示）。`mcp_server.transport='local'`，执行时由 `LocalHandlerClient` 转回原 Handler。
2. **主服务实际注册同步**（`server_py/mcp_skill/builtin.py` + `POST /internal/builtin-skills/sync`）：主服务启动时把当前 Dispatcher 实际注册的内置能力（含 slots/keywords）同步到商店，覆盖商店端轻量快照的简化版本。`ChatService.__init__` 中调用，失败不阻塞（`StoreUnavailable` 时降级，后续聊天请求中通过 `_builtin_sync_done` 标志重试）。

内置能力 `always_enabled=True`，用户端默认启用；用户可在手机端停用（落一条 `enabled=0` 的偏好行），停用后不进 `/me/skills/sync` 返回列表，服务端重建图时排除。

### 6.2 三态语义与状态隔离

**三态**：未选购 → 已选购（enabled=0）→ 已启用（enabled=1）。
- 停用保留选购，退订才移除（级联删凭证）；
- 启用未选购技能时自动创建选购行（INSERT）；
- 管理员下架技能时用户行被保留，可停用/退订但不能新建启用/配凭证（409），实现管理员轴与用户轴的状态隔离；
- 已下架但已选购的技能出现在 `GET /me/skills/detail`（含已下架），手机端渲染「已下架」卡。

### 6.3 热插拔（≤30s 生效）

任何启停/配凭证/上架/下架/删除操作都在同一事务内 version+1（`_bump_version` / `_bump_skill_holders`）；`SkillRegistry` 以 TTL 30s 缓存版本与技能列表，网络 IO 在锁外避免串延迟；版本变化时 `ChatService` 只重建该用户的路由图，并关闭旧 MCP 连接防止线程泄漏。

**关键设计点**：
- **版本回退保护**：复用条件 `hit[0] >= version`（而非 `==`），某线程 resolve 到旧版本但另一线程已写入更新图时，直接复用新图，避免"旧版本覆盖新版本"；
- **锁内重验版本**：`ChatService._assistant_for` 在锁内重新比对版本，杜绝并发重复构建图；
- **LRU 上限**：`MAX_GRAPHS=200`，超出淘汰最久未用用户的图并关闭其所有 MCP 连接；
- **冲突过滤**：撞内置 intent 的 MCP 技能在装配时静默跳过（商店上架 409 是第一道，服务端是第二道双保险）；
- **replaces 顶替**：用户启用声明了 `replaces` 的技能后，对应内置 intent 从 dispatcher 和计划器白名单剔除（保留 `chitchat` 作为无工具时的安全兜底）。

### 6.4 动态凭证系统

`credentials.type` = `none` | `byok`；`schema` 声明字段：`secret` / `string` / `number` / `select` / `boolean` / `textarea` / `file`，配合 `inject{where: header|query, name, prefix}` 声明注入位置。

- 手机端按 schema **动态渲染表单**，加新 MCP 零端上改动；
- **AES-256-GCM 加密落库**，AAD 绑定 `user_id:skill_id` 防跨用户/跨技能互换密文；
- **敏感字段留空=保留旧值**：脱敏 GET 不回传明文，用户只改非敏感字段保存时不会清掉已存密钥；
- **脱敏返回**：`GET /me/credentials` 中 secret/textarea/file 字段值置 null，其余非敏感字段返回明文供表单预填；
- **明文仅内部使用**：`GET /me/credentials/plain` 仅供服务端连接建立时调用，手机端不可访问；
- **连接建立时现取明文注入**请求头或 URL（`SkillCredentialProvider` 无缓存），消除"改了 key 仍取旧值"的边缘；
- 缺 `STORE_MASTER_KEY` 时写凭证 **fail-closed** 500，不写入明文。

**inject 三种写法**：
- Bearer 鉴权（最常见）：`{"where":"header","name":"Authorization","prefix":"Bearer "}` → `Authorization: Bearer <值>`
- 非 Bearer 头（如东财）：`{"where":"header","name":"em_api_key"}` → `em_api_key: <值>`
- Query 参数：`{"where":"query","name":"region"}` → 拼进 URL `?region=cn`

### 6.5 路由确定性

- **关键词收窄**：`manifest.keywords` 命中即确定性路由到该技能（修复内置抢跑）；
- **顶替内置**：`manifest.replaces` 声明顶替的内置 intent，装配时从 plannable 集剔除；
- **白名单修复**：`allowed_intents = dispatcher.intents | _PLANNABLE_INTENTS`（不再用静态常量挡 MCP 意图）；
- **降级**：商店宕机 → 退回内置技能；MCP 不可达 → 该技能返回「暂不可用」；缺凭证 → 提示「去配置」。

### 6.6 Gemini 识别与路由（添加新工具流程）

**核心机制**：Gemini 识别的是「技能（intent）」而非「工具」——每个技能被编译成一个 Gemini function 声明，通过 function calling（mode=ANY）一次调用同时得到「意图 + 槽位」，再路由到该技能的 `entry_tool`。意图列表在运行时由 Dispatcher 从已注册 handler 动态收集传入分类器，因此添加新技能无需改分类器代码。

**识别 - 路由四步链路**：
1. **装配 manifest**：商店 `/me/skills/sync` → manifest{intent, description, entry_tool, tools, keywords, query_slot} → 每个 manifest 生成一个 `MCPHandler`（内置能力用 `LocalHandlerClient`，远程用 `McpToolClient`）；
2. **包装成 Handler 契约**：`MCPHandler.spec()` → `IntentSpec(intent, description, slots, keywords)`；manifest.tools 的 JSON Schema 转成 `SlotSpec` 列表（required 读顶层数组，类型收敛为 string/integer），分类器零改动；
3. **编译 function 声明**：`classifier._declaration()` 把每个技能编译成 Gemini functionDeclaration：`{name=intent, description=技能说明, parameters=slots 参数 schema}`——Gemini 靠 description 语义理解技能；
4. **Gemini 识别 + 路由**：`choose_function(query, declarations=所有技能, mode=ANY)` → `FunctionCall(name=intent, args=slots)` → 函数名=意图、参数=槽位 → `Route(intent, slots)` → Dispatcher 定位对应 `MCPHandler.handle()` → `client.call_tool(entry_tool, args)` 真正连 MCP。

**关键设计点**：

| 设计 | 作用 |
|---|---|
| 意图列表运行时传入 | 加技能不改分类器代码，零开发成本 |
| description 即函数说明 | Gemini 纯靠语义判断，无硬编码映射 |
| mode=ANY + function calling | 一次调用拿意图+槽位，省一半延迟与调用成本 |
| multi-turn 意图继承 | 带最近 3 轮裁剪 history，跟进式输入继承上轮意图与槽位 |
| keywords 锁定 / replaces 顶替 | 命中即确定性路由；可顶替内置意图，保证路由确定性 |
| KeywordClassifier 兜底 | Gemini 不可用 / 返回非法时回退，只出意图不出槽位 |

**边界：识别的是「技能」而非「工具」**：
当前实现里，Gemini 只负责把用户 query 路由到「技能（intent）」，真正调用的是 manifest 里的 `entry_tool`（单个主工具）。因此多工具 MCP（如麦当劳 **30 个工具**）目前也只通过 entry_tool 一个入口调用；多工具路由 / 拆技能属于后续方向（见「已知限制」）。

> 来源：`server_py/routing/{classifier, gemini}.py` + `server_py/mcp_skill/{assembly, handler, manifest, client}.py`

## 七、如何接入一个新 MCP（详细五步）

> **推荐方式**：官方目录（§7.1）—— 开发写 JSON 走评审，管理员只上架/下架，可追溯、可版本管理。
> **仅逃生**：自定义 MCP（§7.2）—— 管理后台 probe → 手拼 manifest，不走评审，仅用于临时调试、目录外的私有 MCP。

### 7.1 官方目录（推荐，10 分钟）

**五步：写 JSON → 获取 tools schema → 同步 → 上架 → 启用验证。**

#### 第 1 步：写 `skill_store/connectors/<你的>.json`

最小模板（无凭证 MCP）：

```json
{
  "skill_id": "translate-mcp",
  "name": "文本翻译（MCP）",
  "icon": "🌐",
  "description": "自然语言翻译，支持中英日韩等多语言互译",
  "intent": "translate_mcp",
  "pc_only": false,
  "entry_tool": "translate",
  "query_slot": "text",
  "keywords": ["翻译", "翻译成", "英文怎么说"],
  "replaces": [],
  "mcp_server": { "transport": "http", "url": "https://你的-mcp-地址/mcp" },
  "credentials": { "type": "none", "schema": [] },
  "tools": [
    {
      "name": "translate",
      "description": "文本翻译工具",
      "input_schema": {
        "type": "object",
        "properties": {
          "text": { "type": "string", "description": "待翻译文本" }
        },
        "required": ["text"]
      }
    }
  ],
  "default_status": "inactive"
}
```

**关键字段填写要点**：

| 字段 | 怎么填 | 注意事项 |
|---|---|---|
| `skill_id` | 全局唯一，建议 `<名称>-mcp` | 不能与已有技能重复 |
| `intent` | 全局唯一，小写下划线 | **不能撞 22 个内置 intent**（撞了上架 409）；不能撞其他 active 技能 |
| `entry_tool` | MCP server 的入口工具名 | 必须与 MCP server 实际工具名一致 |
| `mcp_server.url` | MCP 真实端点 | 很多 MCP 官网首页不是端点，真实端点常带 `/mcp` 后缀 |
| `keywords` | 命中即确定性路由 | 建议 3~10 个覆盖用户典型说法 |
| `default_status` | 新技能建议 `inactive` | `active`=同步即上架，`inactive`=待上架（缺省） |

需凭证 MCP（byok）把 `credentials` 改为 schema 声明，详见 §6.4。

#### 第 2 步：获取 entry_tool 的 input_schema

`tools` 数组至少要包含 `entry_tool` 的完整 `input_schema`。获取方式二选一：

- **管理后台 probe 发现（推荐）**：打开管理后台 → 展开「高级：添加自定义 MCP」→ 填 MCP 地址 → 点「发现工具」→ 从结果复制工具的 name/description/input_schema。需鉴权的填临时 Token 或自定义请求头 JSON（临时 Token 不保存）。
- **手动调用 list_tools（脚本）**：

```python
import asyncio
from mcp import ClientSession
from mcp.client.streamable_http import streamable_http_client

async def main():
    url = "https://你的-mcp-地址/mcp"
    async with streamable_http_client(url) as (r, w, *_):
        async with ClientSession(r, w) as session:
            await session.initialize()
            res = await session.list_tools()
            for t in res.tools:
                print(t.name, dict(t.input_schema))

asyncio.run(main())
```

#### 第 3 步：同步进库

改完 `connectors/*.json` 后二选一：
- **管理后台点「重新同步目录」**（推荐，免重启）→ 调用 `POST /skills/sync-all`，同时同步 connector 目录与内置能力；或
- 重启商店（启动时 lifespan 自动同步 connector + builtin）。

**验证同步成功**：

```bash
# 管理员视角：检查新技能是否在库中（含已下架）
curl http://127.0.0.1:9000/skills/admin | python -m json.tool
```

确认返回列表中包含新技能的 `skill_id`，`publisher=catalog`，`status=inactive`（或你设的 default_status）。

#### 第 4 步：上架

1. 打开管理后台 `http://<PC IP>:9000/`
2. 在统一技能目录表中找到新技能（状态为 ⚪ 已下架）
3. 点「上架」按钮 → 状态变为 🟢 已上架

**验证上架成功**：

```bash
# 用户端目录：仅 active 技能，应包含新技能
curl http://127.0.0.1:9000/skills | python -m json.tool
```

#### 第 5 步：手机端启用 + 配凭证 + 语音验证

1. 打开手机 App → 技能商店 → 找到新技能卡片 → 打开**启用开关**
2. 若是 byok 技能，**立即自动弹出凭证表单** → 填 API Key 等字段 → 保存
3. 等待 **≤30s** 热插拔生效
4. 说触发话术验证，确认意图路由到新技能且返回正确数据

**命令行验证（无需手机）**：

```bash
curl -X POST http://127.0.0.1:8000/chat \
  -H "Content-Type: application/json" \
  -d '{"query":"你的触发话术","user_id":"test-user-001","session_id":"s1","platform":"mobile"}' \
  | python -m json.tool
```

检查返回的 `intent` 字段是否为新技能的 intent。

#### 麦当劳 MCP manifest 实例（byok 单字段 Bearer）

用户启用时表单只需填一个 MCP Token → AES-GCM 加密存储 → 服务端连接 `mcp.mcd.cn` 时注入 `Authorization: Bearer <token>` → 语音「附近有麦当劳吗」命中 `mcdonalds_order` → 调 `query-nearby-stores`。

```json
{
  "skill_id": "mcdonalds-mcp",
  "name": "麦当劳点餐",
  "icon": "🍔",
  "intent": "mcdonalds_order",
  "entry_tool": "query-nearby-stores",
  "query_slot": "address",
  "keywords": ["麦当劳", "金拱门", "麦乐送", "麦当劳门店", "麦当劳优惠券"],
  "mcp_server": { "transport": "http", "url": "https://mcp.mcd.cn" },

```

**现成范例**（拷一个改最省事）：

| 范例文件 | 凭证形态 | 适用场景 |
|---|---|---|
| `weather.json` | none | 无鉴权 MCP，最简单 |
| `stock.json` | none | 无鉴权 MCP |

#### 快速检查清单（发布前必过）

- [ ] `skill_id` 全局唯一
- [ ] `intent` 全局唯一，**不撞 22 个内置 intent**
- [ ] `entry_tool` 与 MCP server 实际工具名一致
- [ ] `mcp_server.url` 是真实 MCP 端点（不是官网首页）
- [ ] `tools` 数组包含 entry_tool 的完整 `input_schema`
- [ ] byok 技能的 `credentials.schema` 每个字段都有 `inject`
- [ ] `keywords` 覆盖用户典型说法（3~10 个）
- [ ] `default_status` 新技能建议 `inactive`（待上架）
- [ ] 同步后管理后台能看到新技能（`GET /skills/admin`）
- [ ] 上架后用户端目录能看到新技能（`GET /skills`）
- [ ] 手机端启用后 ≤30s 语音调用成功（`intent` 正确）

### 7.2 自定义 MCP（逃生通道，5 分钟）

不走目录，直接用管理后台 probe → 手拼 manifest。适合：临时调试、目录外的私有 MCP、快速验证。

**四步：probe 发现工具 → 填写 manifest → 发布 → 验证。**

1. **打开管理后台高级区**：`http://<PC IP>:9000/` → 展开「高级：添加自定义 MCP」
2. **probe 发现工具**：填 MCP server 地址 → 需鉴权的填临时 Token（Bearer）或自定义请求头 JSON（非 Bearer，如 `{"em_api_key":"xxx"}`）→ 点「发现工具」→ 成功后显示工具列表，发布表单自动展开
3. **填写并发布 manifest**：确认/修改 skill_id、intent（不能撞内置，输入时实时提示⚠️）、名称、关键词、credentials JSON → 点「新增（发布）」
4. **验证 + 使用**：发布后出现在统一目录表中（publisher 非 catalog/builtin，**有删除按钮**），status=active。后续启用、配凭证、语音验证同 §7.1 第 5 步。

**probe 常见错误与处理**：

| 错误提示 | 原因 | 处理 |
|---|---|---|
| 鉴权失败（HTTP 401/403） | 临时 Token 缺失或无效 | 填正确的 Token 或请求头 |
| 该地址返回的是网页 | 填了管理网页而非 MCP 端点 | 找真实 MCP endpoint（常带 `/mcp` 后缀） |
| 地址不存在（HTTP 404） | URL 路径错误 | 检查 URL 路径 |
| 该地址不是 MCP endpoint（HTTP 405） | 地址不接受 MCP 握手 | 确认地址支持 streamable-http |
| 请求过频（HTTP 429） | 限流 | 稍后重试 |
| 连接超时（>30s） | MCP server 不可达或太慢 | 确认网络；真实麦当劳 MCP list_tools 约 18s 属正常 |

**自定义 MCP 与官方目录技能的区别**：

| 维度 | 官方目录（§7.1） | 自定义 MCP（§7.2） |
|---|---|---|
| 存储 | `connectors/*.json` 文件（可版本管理、可评审） | 仅数据库（无文件追溯） |
| publisher | `catalog` | `poc` 等（非 catalog/builtin） |
| 管理后台操作 | 上架/下架（**不可删除**） | 上架/下架/**删除** |
| 适用场景 | 正式接入 | 临时调试、私有 MCP |

## 十一、platform（OAuth 托管）商用计划

**目标**：在现有 byok 骨架之上，把凭证来源从「用户自己填 Key」升级为「OAuth 委托授权 + Token Broker 托管」，用户点一下授权即可，把"用户自己填 key"的门槛降到最低。依据项目 OAuth 技术分析报告（2026-07-23）。

### 11.1 byok 的商用痛点

- **门槛高**：普通用户不知道去哪申请第三方 API Key；
- **体验差**：手动复制粘贴，无撤销/过期管理；
- **不安全**：Key 是长期全权限 Bearer 凭据，泄漏后果接近密码泄漏。

### 11.2 OAuth 委托授权推荐基线

手机端作为 OAuth Native Public Client，用系统浏览器 / 第三方授权 App 完成 Authorization Code + PKCE；回调只返回短时一次性 Code（不是 Key）。长期授权由第三方 Token Broker 或 SDK 托管，手机只取短期、最小权限、限定资源的 Access Token；条件允许用 DPoP 绑定端侧不可导出私钥。

**眼镜侧约束**：眼镜不保存 Refresh Token；我方云不保存/转发 Token、不代理第三方 API、不接收私人行程；订票 / 退票 / 支付不能凭一次长期授权静默执行，必须单笔确认。

### 11.3 落地到技能商城的改造点

| 环节 | 现状（byok） | 改造成 platform |
|---|---|---|
| connectors JSON | `credentials.type="byok"` + schema | 加 platform 配置（authorize_url / token_endpoint / scope / client_id 等） |
| 手机端表单 | 按 schema 渲染字段填 Key | 换成「去授权」按钮 → 走 OAuth 流程 |
| 凭证存储 | AES-GCM 存 Key | 存 Token Broker 引用 / session handle（真实 Token 对宿主不可见），AES-GCM + AAD 沿用 |
| 服务端注入 | 连接建立时注入 Key | 向 Broker 换短期 Access Token → 注入 header/query（框架复用） |
| 版本联动 | 保存即 bump | 授权建立/撤销也 bump（复用现有热插拔） |
| 安全 | — | 回调校验 state/iss、PKCE、DPoP、Token 不进 LLM/日志 |

**复用**：现有动态凭证骨架——AES-GCM 加密、AAD 防互换、版本 bump、连接级注入——全部沿用，只是"存的/注入的"从用户 Key 变成平台 Token，是渐进式升级而非重写。

### 11.4 分阶段落地路径

| 阶段 | 内容 | 验收点 |
|---|---|---|
| M1 | connectors 支持 `credentials.type="platform"` 声明（authorize/token/scope） | 能声明、能展示「需授权」状态 |
| M2 | 手机端接入 OAuth Native Client（Authorization Code + PKCE），走系统浏览器 | 用户点授权 → 第三方登录 → 回到 App 建立授权 |
| M3 | Token Broker/SDK 托管 + 服务端换短期 Access Token 注入 | 语音调用第三方带有效 Token |
| M4 | 安全加固：state/iss 校验、DPoP、撤销、Token 不落日志 | 通过安全评审 |
| M5 | 单笔交易确认（订票/支付二次确认） | 高风险操作不静默执行 |

### 11.5 安全红线（报告明确「直接拒绝」）

- 登录回调 URL 直接返回永久 Key / Access / Refresh Token；
- APK / IPA / SDK 内置一份共享 client_secret 并声称机密；
- 一个长期 Token 同时拥有查询、订票、退票、支付权限；
- Token 进入大模型上下文、对话历史、埋点、崩溃日志；
- 把「登录成功 / OAuth 授权 / 订票确认」混成一件事件。

> 来源：`docs/从登录后返回Key到现代委托授权_OAuth技术横纵分析报告.md`（2026-07-23）｜方案：技能商城动态凭证架构

| `keywords` | | 命中即确定性路由到本技能，建议 3~10 个 |

| `always_enabled` | | 内置能力专用，默认 `true`（用户端默认启用，可手动停用） |
| `mcp_server.url` | ✅ | MCP 真实端点（`transport` 是装饰字段，运行时只读 url；内置能力为 `handler://<intent>`） |
| `credentials` | ✅ | `none`（无需）/ `byok`（用户填，schema 声明字段与注入位置） |
| `tools` | ✅ | 至少放 entry_tool 的完整 `input_schema`（含 properties 和 required） |
| `default_status` | | 顶层字段，非 manifest 成员；`active`（同步即上架）/ `inactive`（待上架，缺省）；新技能建议 `inactive` |
| `pc_only` | | 可声明仅 PC 可见（如 `music_control`） |
