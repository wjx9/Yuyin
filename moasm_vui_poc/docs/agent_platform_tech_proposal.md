# 给"三有一无"的大模型装上手脚眼睛耳朵：Agent 平台零层抽象与全端技术方案

> 整理时间：2026-07-17。
> 定位：基于对 LobeHub / WorkBuddy / Claude 桌面版这类 agent 宿主的共性解剖，确立我们自己的零层抽象，并给出 PC / Web / 手机（含以手机为伴侣宿主的智能眼镜）全端落地的前后端技术选型评估。
> 配套文档：[LobeHub 分析与 VUI 生态考察](./lobehub_analysis_and_vui_ecosystem.md) · [LobeHub 使用 SOP](./lobehub_usage_sop.md) · [Web 栈速成](./web_stack_primer_for_native_devs.md)
>
> **阅读方式**：第一章定抽象（含"记忆归属"的论证），第二章定流程，第三章逐模块选型评估，第四章分端落地，第五章关键工程决策，第六章演进路线。每章开头有【要点】框。

## 全文速览（30 秒版）

- **零层抽象定为五模块 + 一运行时**：① 用户面（请求/呈现）；② 技能注册层（给模型看的"能力目录"）；③ 能力层（端侧 + 云侧的真实执行体）；④ 记忆子系统（**并列的第一等模块**，为可替换的 ④′ 补"一无"）；④′ 大模型（三有一无，随时可替换的下层供应商）；⊕ Harness 运行时（把以上绑定成流程的编排工程，我们的核心自研物）。
- **流程三步的工程化形态**：用户请求 → 快慢双路径路由（意图识别在 LLM 时代主要由模型自身的 function calling 承担，快路径才用轻量分类器）→ harness 执行（上下文组装 → agent loop → 确认与呈现 → 记忆回写）。
- **选型总原则**：协议用开放标准（MCP / SKILL.md），模型层做成可插拔供应商，力气全部押在 harness、记忆、设备上下文三个别人拿不走的地方。
- **分端结论**：Web/PC 用 TS + React/Next.js（+ Electron 壳）；手机伴侣 app 用 **Flutter 壳 + 原生能力模块（Kotlin/Swift）**——伴侣 app 是能力密集型而非内容密集型，团队 Flutter 存量技能 > web 代码复用收益；眼镜按纯 IO 外设建模；云端编排 TS 优先、检索/ML 侧留 Python 旁路。

# 第一章：零层抽象（模块划分）

> 【要点】用户的四层划分成立，做两处修正：① 记忆必须升格为并列的第一等模块——因为它是对可替换模块（大模型）"一无"的补偿，寿命必须长于任何一代模型；但它以三种形态同时投影到技能层和能力层。② 显式补上第五个隐含模块：Harness 运行时——LobeHub/Claude 桌面版这类产品的全部自研价值都在这一层，它不是流程的副产品，是核心资产。

## 1.1 五模块 + 一运行时

```
① 用户面（User Surface）
     用户请求进入 / 结果呈现返回的地方
     形态：聊天框、语音、HUD 卡片、IM 消息、通知
────────────────────────────────────────
⊕ Harness 运行时（编排工程）—— 我们的核心自研物
     路由、上下文组装、agent loop、确认策略、任务生命周期
────────────────────────────────────────
② 技能注册层（Skill Registry）        ④ 记忆子系统（Memory）
     给模型看的"能力目录"                  为 ④′ 补"一无"的横切模块
     - 裸呈现：单个能力直接注册为工具        - 画像（结构化事实）
     - 包装呈现：多能力 harness 工程         - 情景（向量检索）
       打包成一个技能，内部自动多步          - 工作记忆（会话内）
       运行直到出结果                        寿命 > 任何一代模型
────────────────────────────────────────
③ 能力层（Capabilities）—— 真实执行体
     端侧：读写文件、通讯录、已装 app、传感器
     云侧：私域查询（股价/航班/个人 Google Docs/GitHub）、SaaS API
────────────────────────────────────────
④′ 大模型（LLM）—— 三有一无，可替换供应商
     有基本世界常识、有逻辑、有（受限的）上下文输入输出
     无记忆（跨会话无状态）
```

## 1.2 记忆的归属论证（回答"划到 2、3，还是并列"）

**结论：并列为第一等模块，但同时以三种形态投影到 ② 和 ③。**

论证分三步：

1. **为什么不能只是一个技能（②）**：技能是"模型想用才调"的东西。若记忆只是 `remember/recall` 两个工具，则记忆的存取完全依赖模型自觉——模型忘了调 recall，用户的常用地址就"不存在"。真实系统里记忆的**读路径必须由 harness 强制执行**：每轮对话组装上下文时自动检索相关记忆注入，不问模型意见。这就超出了技能层的定义。
2. **为什么不能只是一个能力（③）**：能力层是被动的执行体（一个存储后端确实在这里）。但记忆还有**写路径的策略问题**——每轮对话后提取什么、去重合并、遗忘衰减、冲突消解——这些是编排逻辑，长在 harness 里，不长在存储里。
3. **决定性理由——寿命错配**：④′ 是"随时被替换的下层三有一无模块"（你的原话），而记忆恰恰是替换 ④′ 时**必须无损保留**的东西。一个模块的生命周期约束（必须活过所有模型换代）决定它不能附属于任何按模型生命周期组织的层。所以它是并列的第一等模块。

三种投影形态（工程实现时三者并存）：

| 投影 | 落点 | 用途 |
|---|---|---|
| 存储后端（Postgres + pgvector） | ③ 能力层 | 数据的物理归宿 |
| 自动读写策略（检索注入 + 轮后提取） | ⊕ Harness | 主通道：模型无感知，每轮生效 |
| 显式工具（`remember` / `recall` / `forget`） | ② 技能层 | 补充通道：用户说"记住这个"时模型显式调用 |

## 1.3 对"三有一无"的一个补充

严格说裸模型是"三有二无"：无记忆，也**无手脚**（不能自主触达外部世界）。整个平台工程的本质就是两句话：**技能+能力层补"无手脚"，记忆子系统补"无记忆"**；而"有限上下文"这个约束，决定了两者的接入都必须走"检索式按需注入"而不是"全量塞入"（见 5.2 工具召回与记忆召回——同一个问题的两个实例）。

# 第二章：运行流程（把三步流程工程化）

> 【要点】用户给的三步流程正确，工程化时的关键修正是：LLM 时代的"意图识别+参数提取"主要由模型自身的 function calling 完成（这正是相对 Alexa 时代的代差优势），单独的意图识别模块只服务于快路径；harness 的核心工作在模型看不见的地方——上下文组装与确认策略。

```
1. 用户请求（文字/语音/图像，来自任一用户面）
        ↓
2. 路由（快慢双路径）
   ├─ 快路径：轻量分类器/关键词 → 命中高频头部意图（定时/天气/播放）
   │           → 直接调能力，不进大模型。延迟 <500ms
   └─ 慢路径：进 harness 的 agent loop
        ↓
3. Harness 执行
   3a. 上下文组装（模型看不见的核心工序）：
       system prompt + 记忆检索结果（④ 读路径）
       + 工具召回结果（② 的 top-k 技能 schema，tool RAG）
       + 设备上下文（位置/camera 摘要/正在做的事）
       + 会话历史（受限上下文 → 需截断/摘要策略）
   3b. agent loop：模型输出工具调用意图 → harness 分发给 ③ 执行
       → 结果回填 → 循环，直到模型产出最终答案
       （最简退化形态 = 单能力裸调用一次出结果；
         最复杂形态 = 多步多能力 + 常驻后台任务 + 长期记忆读写）
   3c. 确认策略：写操作（支付/发消息/删除）拦截 → 用户面确认后放行
   3d. 呈现：按用户面渲染（文字/口语摘要/HUD 卡片）
   3e. 记忆回写（④ 写路径）：轮后异步提取值得记的事实，去重合并入库
        ↓
4. （长任务）任务生命周期：派发 → 后台常驻运行 → 进度事件 →
   完成入待审核区 → 用户评论 → 迭代。经 IM/通知渠道回报
```

两条流程级设计规则（来自语音场景分析，对全端适用）：
- **异步任务语义**：超过延迟预算的工作一律转后台任务（"我去办，好了叫你"），不阻塞对话轮次；
- **读写分级**：读操作直通，写操作过确认闸——闸的形态随用户面变（屏幕弹窗 / 口头确认+HUD 摘要）。

# 第三章：逐模块技术选型评估

> 【要点】每个模块给出候选、取舍、推荐。总原则重申：协议用开放标准，模型可插拔，自研力气花在 harness/记忆/设备上下文。

## 3.1 ④′ 大模型接入层

| 决策点 | 候选 | 评估 | 推荐 |
|---|---|---|---|
| 多供应商抽象 | 各厂原生 SDK 直连 / 统一抽象层（如 Vercel AI SDK 或自建薄层） | ④′ 是可替换模块是零层抽象的前提，直连单厂 SDK 会让替换成本扩散到整个 harness | **自建薄抽象**（消息/工具调用/流式三个接口），底下挂各厂 TS SDK；抽象层刻意薄，不追求抹平所有差异 |
| 多模态 | 视觉输入是硬需求（眼镜 camera） | 主力模型必须选带视觉的旗舰系 | 主力选旗舰多模态；快路径/摘要类配小模型分级调度（成本工程） |

## 3.2 ② 技能注册层

- **协议**：MCP（工具）+ SKILL.md（方法包）。理由已在配套文档充分论证：Linux 基金会中立标准、四大模型厂原生支持、三方已有资产零成本迁入；自创协议 = 重演 Alexa Skills Kit 之死。
- **自建扩展**：呈现 profile——技能返回结果附加"如何朗读 / 如何出 HUD 卡片 / 是否需确认"元数据（MCP 生态真空地带，做好可外溢成标准）。
- **"包装呈现"的实现**：多能力打包的复合技能，本体就是一段 harness 子流程（子 agent / 工作流），对模型仍以单工具形态注册——这保持了 ② 的接口一致性：**模型只看到目录，不关心目录项背后是裸能力还是一台小机器**。

## 3.3 ③ 能力层

| 位置 | 机制 | 说明 |
|---|---|---|
| 云侧（私域/SaaS） | 远程 MCP server（Streamable HTTP + OAuth 2.1：强制 PKCE、aud 校验、禁 token 透传） | 股价/航班/Google Docs/GitHub 全走此通道；凭据存 server 侧，模型永远摸不到 token |
| 端侧-PC | 本地进程型 MCP（stdio）+ 桌面壳的 OS 权限 | 读写文件、起进程；web 版天然做不了（浏览器沙箱），必须有桌面壳 |
| 端侧-手机 | OS 官方机制：Android AppFunctions / Apple App Intents，桥接成与 MCP 同构的工具接口 | 已装三方 app 的能力免开发收编；权限偏向 OS 一方助手，OEM 身份是结构性优势，非 OEM 备降级方案（deep link/直谈 SDK） |
| 端侧-眼镜 | 不注册"工具"，注册"上下文提供者" | camera/位置/活动状态是输入流不是被调用物，见 3.5 |

## 3.4 ④ 记忆子系统

| 分层 | 内容 | 存储 | 读写策略 |
|---|---|---|---|
| 工作记忆 | 当前会话状态、任务中间产物 | Redis / 会话库 | harness 全权管理，随会话生灭 |
| 情景记忆 | "上周说过想去青岛" | pgvector（嵌入检索） | 写：轮后异步提取；读：组装上下文时按当前请求检索 top-k |
| 画像/语义记忆 | 常用地址、偏好、关系人、设备清单 | Postgres 结构化表 | 写：抽取器识别稳定事实入表（带来源与置信度）；读：每轮固定注入摘要 |
| 程序性记忆 | 用户纠正过的做法（"以后都用摄氏度"） | 结构化规则 → 注入 system prompt | 显式反馈触发写入，优先级最高 |

工程要点：提取/检索用的嵌入模型与 ④′ 解耦（换主力模型不动记忆库）；遗忘与合并是必做项（无限堆积会毒化检索质量）；用户可见可删（隐私合规 + 信任）。

## 3.5 ⊕ Harness 运行时（核心自研物）

- **形态**：云端服务（主体）+ 端侧薄执行器。自研 agent loop 而不是绑死某框架——loop 本身只有百行量级，复杂度在策略（组装/确认/预算/重试），框架帮不了多少还引入耦合。
- **必备件**：工具召回（tool RAG）、上下文预算管理（截断/摘要）、任务生命周期（常驻/进度/待审核）、确认闸、审计日志（每次工具调用可回放——出事故时的生命线）。

## 3.6 云端基础设施

| 项 | 选择 | 理由 |
|---|---|---|
| 编排服务语言 | **TypeScript（Node）优先** | AI SDK/MCP 生态最厚、与 web 前端共享类型定义；团队正在补 TS，与前端学习投资复用 |
| ML 旁路 | Python 微服务（嵌入、rerank、ASR 后处理等） | Python ML 生态无可替代；以独立服务隔离，不污染主编排 |
| 备选评估 | Kotlin/JVM（团队存量技能强） | 可行但 AI 生态薄一截（SDK 滞后、MCP 实现少），会持续付"翻译成本"；不推荐做编排层 |
| 数据 | Postgres + pgvector（记忆/业务）、Redis（会话/队列）、S3 兼容存储（文件） | 全部行业默认件，LobeHub 同款验证过 |
| 实时通道 | WebSocket（语音双工/事件推送）+ SSE（文本流式） | 语音必须全双工，纯 SSE 不够 |

# 第四章：分端落地与前端技术选型

> 【要点】三类客户端按"内容密集 vs 能力密集"分野选栈：Web/PC 内容密集 → TS+React 一份代码多壳；手机伴侣 app 能力密集 → Flutter 壳 + 原生能力模块（用团队存量技能，放弃 web 代码复用幻想）；眼镜按纯 IO 外设建模，不承载业务。

## 4.1 Web + PC 桌面

| 决策点 | 候选 | 评估 | 推荐 |
|---|---|---|---|
| Web 前端 | React/Next.js / Vue / Flutter Web | React：AI 产品生态事实标准（流式渲染、Markdown、代码高亮组件全是现成的）；Vue 无决定性优势；Flutter Web 首屏与 SEO 硬伤、文本渲染非原生 | **Next.js + React**（LobeHub 同款路线，已被验证） |
| PC 桌面壳 | Electron / Tauri | 桌面壳的存在理由 = 拿 OS 权限（本地文件、起进程、本地 MCP）。Electron：与 web 同一份代码、生态最厚、体积大；Tauri：轻量（Rust 内核）、但 Node 侧生态复用差、团队无 Rust 存量 | **Electron**；性能敏感的本地组件可后期用原生 sidecar 进程补 |
| 桌面端数据 | 本地嵌入式 PGlite（LobeHub 验证过的路线）+ 云同步 | 离线可用 + 隐私敏感数据可留本地 | 同款 |

## 4.2 手机伴侣 app（智能穿戴宿主）——本方案最关键的选型

先定性：伴侣 app 是**能力密集型**应用——BLE/音频管线（低延迟流式采集回传）、唤醒词、前台常驻服务、OS 工具桥（AppFunctions/App Intents）、上下文采集。UI 反而简单（管理面 + 会话视图）。这个定性决定选型权重：**设备能力接入的顺畅度 > web 代码复用率**。

| 候选 | 评估 |
|---|---|
| **Flutter + 原生模块（推荐）** | 团队存量技能（Dart/Flutter/Kotlin/Java 全有）；一份 Dart 代码覆盖双端 UI；能力密集部分本来就必须写原生（AppFunctions 桥是 Kotlin、App Intents 桥是 Swift、低延迟音频要 Oboe/AVAudioEngine），Flutter 的 platform channel / FFI 接原生成熟。**结论：UI 用 Flutter，能力全下沉原生模块** |
| React Native | 与 web 端共享 TS 技能是唯一优势；但音频/BLE/常驻服务生态弱于 Flutter，团队零存量，等于同时学 RN 和补原生——投资翻倍 |
| 双原生（Kotlin + Swift） | 能力接入最顺，但 UI 双份成本；团队 iOS/Swift 存量薄 |
| 只做 PWA | 直接排除：拿不到 BLE 稳定后台、常驻音频、OS 工具桥 |

架构切分（Flutter 壳内）：

```
Flutter（Dart）：管理面 UI、会话视图、商店客户端、设置/授权/审计
   │ platform channel / FFI
原生模块（Kotlin / Swift）：
   ├─ 音频管线：唤醒词（端侧小模型）、VAD、流式采集编码上传
   ├─ 眼镜链路：BLE/WiFi 会话管理、HUD 卡片下发协议
   ├─ OS 工具桥：AppFunctions（EXECUTE_APP_FUNCTIONS）/ App Intents
   ├─ 上下文提供者：位置、日程、活动识别 → 事件流上报
   └─ 常驻：前台服务（Android）/ 后台模式申报（iOS）
```

## 4.3 眼镜端

- **建模原则**：纯 IO 外设，不承载业务逻辑（与零层抽象一致：它只属于①用户面 + ③的传感器部分）。
- **技术形态随硬件定**：MCU/RTOS 方案（C/C++，音频编解码 + BLE 协议栈 + 简单 HUD 渲染器）或 Android 基座方案（AOSP 裁剪，原生 app 做 IO 代理）。
- **需要自定义的两个协议**（走 BLE/WiFi，与伴侣 app 之间）：
  1. 上行：音频帧流 + 传感器事件（含 camera 帧的按需抓取——持续回传功耗不可行，由 harness 按需触发拍摄）；
  2. 下行：TTS 音频流 + **HUD 卡片描述**（声明式卡片 DSL：标题/正文/图标/确认按钮，对应 3.2 的呈现 profile——眼镜只渲染，不理解）。
- eSIM 独立形态：把伴侣 app 的宿主角色搬进眼镜 SoC，软件分层不变，上述协议退化为进程内接口——**架构按分离设计，独立形态是其子集**。

## 4.4 一致性收口

三端共享的东西收敛到两处，避免三端三套逻辑：
- **服务端 harness**：路由、编排、记忆、确认策略全在云端，端侧只做 IO 与本地快路径——换端不换脑子；
- **共享协议包**：工具 schema、HUD 卡片 DSL、事件流格式，用一份 schema 定义（TS 侧生成类型 + Dart 侧生成模型），杜绝手写两份漂移。

# 第五章：关键工程决策点（做错会返工的地方）

> 【要点】五个决策点：延迟预算决定双路径；两个"召回"问题同构；确认闸随用户面变形；安全边界三条铁律；可观测性从第一天做。

1. **延迟预算 → 快慢双路径是硬架构不是优化**：语音轮次 1–2s 上限。快路径（端侧分类器直达能力）与慢路径（agent loop）在路由层分流，慢路径超时自动转异步任务。不要指望"模型变快后就不用了"——头部高频意图走快路径同时也是成本工程。
2. **工具召回与记忆召回是同一个问题**：都是"有限上下文 vs 无限候选"，都用嵌入检索 top-k 注入解决。工程上合并为一个"上下文组装服务"，统一管预算分配（技能 schema 占多少 token、记忆占多少、历史占多少）。
3. **确认闸的形态设计**：写操作分级（低危：口头确认即可；高危如支付：HUD 展示结构化摘要 + 明确口令）。闸的判定依据来自技能注册时的权限 manifest，不依赖模型自觉。
4. **安全三铁律**：模型永远摸不到凭据（token 只存在能力层）；端侧工具执行有沙箱/白名单（尤其 PC 文件读写）；每个技能的 scope 在安装时声明、在管理面可审计——我们是设备厂商，一次凭据事故烧的是硬件品牌。
5. **可观测性从第一天做**：每轮的上下文组装快照 + 工具调用序列 + 模型输入输出全量落审计日志（脱敏后）。agent 系统的调试本质是"回放那一轮的完整上下文"，没有这个，线上问题不可复现。

# 第六章：演进路线

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **Phase 0：骨架** | 云端 harness（薄 agent loop + 模型抽象层）+ Web 端会话界面；1P 能力按 MCP 形式内部定义（天气/提醒/设备控制） | 一条"请求→工具调用→呈现"链路全通，模型可一键切换供应商 |
| **Phase 1：记忆与语音** | 记忆子系统四层落地；手机伴侣 app（Flutter 壳）+ 音频管线 + 快慢双路径；HUD 卡片协议与眼镜联调 | 跨会话记住画像事实；语音轮次快路径 <500ms、慢路径首响 <2s |
| **Phase 2：Top 三方深接** | 远程 MCP + OAuth 2.1 通道；与头部能力方白手套集成（联合调优 + 专属卡片 + SLA）；OS 工具桥接入（AppFunctions/App Intents） | 3–5 个高频三方场景端到端可用，写操作确认闸全覆盖 |
| **Phase 3：开放长尾** | 技能注册表 + 审核/签名/权限 manifest；接受三方远程 MCP server 提交；tool RAG 上线支撑千级技能池 | 三方自助提交→审核→上架→被模型隐式路由调用，全程无需用户"逛商店" |

**收束回零层抽象**：这条路线的每一步都在做同一件事——④′（模型）保持可替换，②③（技能与能力）尽量用开放标准收编存量，把自研密度集中在 ⊕（harness）和 ④（记忆），再加上一个只有我们有的输入：设备第一视角上下文。**平台的护城河不在任何单个模块里，而在"上下文组装"这道工序上——谁掌握的上下文最好，同一个三有一无的模型在谁手里就表现得最聪明。**
