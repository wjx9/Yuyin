## 1. 讨论背景

### 1.1 起源

讨论起源于 8/27-8/28 高德地图预研群聊，参与人员包括：

- **陈文俊（Django）**：方案主导，提出端侧能力抽象 + 语音助手主导编排的核心思路
- **欧阳宇翔**：提出"用户只说开始导航不说目的地怎么办"的边界问题
- **陈振业**：大模型/语音助手侧，讨论陷入子 Agent 的体验问题
- **赵凯**：提出眼镜侧（0x20）是否需要适配导航逻辑的疑问
- **刘帅**：端侧开发，负责代码实现（分支 `sageone/amap_dev`）
- **马俊麒**：产品侧，讨论产品层面的解决方案

### 1.2 原始需求

在 demo 中接入高德导航 agent + 高德导航 SDK，实现语音导航功能。核心挑战是：**用户在等待选择 POI 地址时，可能不按套路出牌去做别的闲谈，这个场景怎么处理好是重点。**

## 2. 核心共识（群聊讨论结论）

### 2.1 端侧能力抽象

从端侧视角，手机 App 只提供有限的导航相关能力接口：

1. `query_poi_list(destination="大新")` → 返回 POI 地址列表
2. `start_navigation(selected_poi)` → 返回导航成功/失败
3. （长远）`start_navigation_directly(destination="大新")` → 直接开始第一个 POI 的导航

余下主要需要语音助手来适配和编排。

### 2.2 语音助手主导编排

从语音助手视角，需要做：

1. 用户指令"开始导航到大新" → 识别导航意图 destination=大新 → 调用端侧 `query_poi_list`
2. 拿到 POI 地址后主动询问用户选第几个（地址为空报错；地址唯一直接导航）
3. 用户选择后调用 `start_navigation`

### 2.3 避免无提示地"陷入"子 Agent

**这是整个讨论最核心的共识**：

> 一定要避免毫无提示地将语音助手"陷入"高德等子 Agent。因为用户与语音助手问答可能是跳跃的、不按套路出牌的，高德 Agent 能力在非导航场景一定弱于雷鸟语音助手（或至少表现不一），无脑无提示地陷入高德 Agent 接管语音问答，会对用户预期造成干扰。

**解决方案**：高德端侧 Agent 只被抽象为几个有限的端侧导航相关能力，给雷鸟语音助手使用；语音助手还需要感知端侧导航状态，以更好使用这些能力。

### 2.4 临时方案 vs 正式方案

- **临时方案（当前）**：一旦意图命中，不做交代直接陷入子 Agent（从第 11 步开始，大模型不再介入当次启动导航流程的后续，走高德 Agent 选 POI 地址，端侧自己触发正式开始导航）
- **正式方案（长期）**：语音助手主导对话编排，端侧只提供有限能力接口，避免无提示陷入子 Agent

当前文档（v1.2）是**正式方案**的技术设计。

### 2.5 导航状态机

端侧要维护一个"是否在导航中、导航路线"的导航状态机，状态机中的参数要方便被填充到每次用户语音指令的公共参数中。未来公共参数一定会携带"当前是否正在导航"。

## 3. 5 个边界场景定义

这是整个方案需要覆盖的核心场景，也是评估方案可行性的基准：

### 场景 1：用户说"开始导航"（没提供导航目的地）

- **期望**：识别到导航意图但缺少参数（目的地），语音助手回复"请问要去哪里"
- **后续**：待用户说出目的地"大新"后，开始 POI 地址列表搜索

### 场景 2：用户说"帮我导航到大新，直接导航，不要废话"

- **期望**：跳过 POI 地址列表选择，直接开始第一个 POI 地址的导航

### 场景 3：用户说"导航到 xxx"（xxx 是极端的无法搜到任何 POI 的词）

- **期望**：语音助手正确应答"找不到 xx，无法导航"

### 场景 4：出现 POI 地址列表后，用户说"开始导航"（没有按照讨论说第 N 个地址）

- **期望**：能直接按照第一个地址开始导航

### 场景 5（核心场景）：出现 POI 地址列表后，用户不按套路出牌，说"帮我看下我的闹钟"

- **期望**：语音助手使用自己的能力处理闹钟请求，而不是将用户意图给高德 Agent 处理
- **重点**：这是整个方案的核心难点，用户在等待选择地址时去做别的闲谈，怎么处理好

## 4. 技术选型演变过程

整个讨论过程中，技术选型经历了多次反复：

### 4.1 阶段一：纯 SDK + 工具封装（最初方案）

- **方案**：端侧只封装高德导航 SDK 的原子接口（`query_poi_list`、`start_navigation`），云侧自己做完整的导航对话编排和状态机
- **优点**：完全可控，对话体验一致，非导航意图直接由主助手处理
- **缺点**：云侧开发量大，需要自己实现 POI 搜索与选择交互、导航对话状态机等
- **文档版本**：v1.0（纯 SDK 方案，12 章+2 附录）

### 4.2 阶段二：用户反馈"目前正在做，只用高德 SDK，不用 agent SDK，按工具处理"

- 用户明确表示当前实现方向是纯 SDK 方案，认为"这可以做到实时的导航"
- 评估了纯 SDK 方案的可行性，确认 4 步正常导航流程完全可以胜任

### 4.3 阶段三：用户问"高德 agent"，解释 Agent vs SDK 区别

- 解释了高德 Agent SDK 与导航 SDK 的区别：Agent SDK 内置导航域完整对话能力，SDK 只提供原子能力
- Agent SDK 优点：端侧开发量小，导航域对话成熟稳定；缺点：黑盒不可控，非导航意图处理需要设计回退机制

### 4.4 阶段四：用户最终决定"引入高德 Agent SDK 的技术方案"

- 用户明确要求引入 Agent SDK 方案，写成技术文档，包括链路、方案、技术选型等
- 重写完整文档（v1.0 引入 Agent SDK 版本，16 章+4 附录）
- **核心设计**：对话控制权交接机制（主助手 ↔ 高德 Agent），两个控制方 `primary` / `amap_agent`

### 4.5 阶段五：补充 ASR 语音识别服务设计

- 用户提供高德 AIoT SDK ASR 服务资料（`https://aiot.amap.com/rest/aiot/asr`）
- 补充第 16 章 ASR 设计，明确"只要在 APP 端实现"的范围约束
- 文档版本更新到 v1.1

### 4.6 阶段六：5 个场景技术路径评估 + 落实兜底方案

- 逐一评估 5 个场景的技术可行性，识别出场景 5（非导航意图）是最大风险点
- 核心结论：不能完全依赖高德 Agent SDK 的非导航意图回退能力，必须在云侧保留前置判断和兜底逻辑
- 落实评估结论到文档：新增云侧前置判断层、5 个场景全部补充兜底方案、新增 POC 验证清单
- 文档版本更新到 v1.2（当前最终版本）

## 5. 方案评估结论

### 5.1 5 个场景可行性评估

| 场景 | 可行性 | 核心依赖 | 风险等级 | 是否需要兜底 |
|---|---|---|---|---|
| 1. 无目的地反问 | ✅ 可以完成 | Agent 反问能力 | 低 | 可选 |
| 2. 直接导航 | ✅ 可以完成 | `direct_navigation` 参数 | 中 | **需要** |
| 3. 搜不到报错 | ✅ 基本可以完成 | Agent 空结果处理 | 中 | **需要**（话术覆盖） |
| 4. 列表后说"开始导航" | ✅ 可以完成 | Agent 状态消歧 | 中 | **需要**（云侧前置转换） |
| 5. 非导航意图回退 | ⚠️ 有条件可以完成 | Agent 非导航意图检测 | **高** | **必须**（云侧前置判断） |

### 5.2 核心结论

**5 个场景技术上都可以完成，但场景 5（非导航意图）是最大的风险点，不能完全依赖高德 Agent SDK 的回退能力。**

**关键保障**：云侧前置判断层——在转发给 Agent 之前，云侧规则引擎+大模型先做一次轻量意图判断，高置信度非导航意图直接不转发，由主助手处理。这个方案不依赖 Agent SDK 的任何特殊能力，100% 可控。

### 5.3 正常导航流程（4 步）评估

对于最基础的正常流程：
1. "导航去大新" → 搜索 POI
2. 返回地址列表，询问选第几个
3. 选第一个
4. 开始导航

**结论：完全可以胜任，这是最基础的正常流程。** 新方案（纯 SDK + 工具封装 或 引入 Agent SDK）对这个流程都没有任何影响。

## 6. 最终方案核心设计决策

### 6.1 技术选型

**引入高德 Agent SDK**，端侧集成高德 Agent，Agent 内部封装高德导航 SDK。

### 6.2 实现范围

**所有导航能力（Agent SDK / 导航 SDK / ASR）仅在手机 App 端实现**，眼镜端不集成任何高德 SDK，仅通过手机端获取导航状态和 HUD 展示数据。

### 6.3 核心设计：对话控制权交接机制

两个控制方：
- `primary`（主语音助手）：默认控制方，处理全局意图
- `amap_agent`（高德 Agent）：导航域对话控制方

控制权转移触发条件：
- 进入 Agent：识别到导航意图
- 退出 Agent：导航结束 / 用户取消 / 超时
- 非导航意图回退：Agent 识别到超出能力范围，主动交还控制权

### 6.4 核心设计：云侧前置判断层（安全网）⭐

在 Agent 持有控制权期间，云侧**不直接无脑转发**用户输入给 Agent，而是先经过一层轻量意图判断：

1. **规则引擎快速判断**：关键词匹配高置信度非导航意图 → 直接拦截，主助手处理
2. **大模型兜底判断**：规则未命中时，大模型轻量分类（>0.9 置信度非导航）→ 同样不转发
3. **模糊意图转发**：无法明确判断或导航域意图 → 才转发给 Agent
4. **Agent 回退兜底**：Agent 识别到非导航意图返回 `handover_requested=true` → 云侧回退

**这是 5 个边界场景全部可覆盖的关键保障，不依赖 Agent SDK 的任何特殊能力。**

### 6.5 端侧能力接口（5 个）

| 接口 | 说明 |
|---|---|
| `enter_agent` | 进入高德 Agent，初始化导航对话 |
| `agent_dialog` | 向 Agent 发送一轮用户对话 |
| `exit_agent` | 主动退出 Agent，清理会话 |
| `stop_navigation` | 停止当前导航（控制接口，不经过对话交互） |
| `query_nvi_about` | 导航中查询沿途相关地点 |

### 6.6 端云通信消息类型（6 种）

| 消息类型 | 方向 | 用途 |
|---|---|---|
| `capability_call` | 云→端 | 发起能力调用 |
| `capability_ack` | 端→云 | 确认已接收/拒绝 |
| `capability_result` | 端→云 | 异步返回业务结果 |
| `handover_event` | 端→云 | Agent 发起控制权交接事件 |
| `navigation_event` | 端→云 | 导航状态变更事件 |
| `capability_register` | 端→云 | 连接时上报支持的能力列表 |

### 6.7 状态机设计

- **控制权状态机**（云侧维护）：`PRIMARY` / `AMAP_AGENT`
- **Agent 对话状态机**（端侧维护，云侧感知）：`WAITING_DESTINATION` / `POI_SEARCHING` / `WAITING_POI_SELECTION` / `NAV_STARTING` / `NAVIGATING` / `COMPLETED`
- **导航执行状态机**（端侧维护）：`NOT_NAVIGATING` / `NAVIGATING`

### 6.8 ASR 语音识别

- 采用高德 AIoT SDK ASR 服务（`https://aiot.amap.com/rest/aiot/asr`）
- 在手机 App 端完成语音转文字，文字上传云侧（不传音频）
- 支持格式：PCM/WAV/OPUS/SPEEX/AMR/MP3/AAC，采样率 16000Hz（默认）
- 建议参数：标点预测、逆文本归一化、VAD、语气词过滤全部开启

## 7. POC 验证清单

POC 阶段必须验证以下 7 项高德 Agent SDK 能力：

| 编号 | 验证项 | 对应场景 | 不支持时的兜底 |
|---|---|---|---|
| V1 | 无目的地时是否主动反问 | 场景 1 | 云侧前置：destination=null 时不进入 Agent，主助手直接反问 |
| V2 | 是否支持 `direct_navigation` 参数 | 场景 2 | 进入后紧接着发"直接选第一个"；或云侧自己先搜 POI 取第一个再启动 |
| V3 | 空结果时的返回格式和话术 | 场景 3 | 云侧检查 poi_list 为空时覆盖 Agent 话术，统一主助手播报 |
| V4 | 状态依赖消歧能力 | 场景 4 | 云侧前置：WAITING_POI_SELECTION 状态下把"开始导航"自动转成"第一个"再转发 |
| V5 | ⭐ **非导航意图回退能力（最关键）** | 场景 5 | **云侧前置判断层作为主方案**，Agent 回退仅作为兜底 |
| V6 | Agent 话术是否可配置 | 品牌一致性 | 关键节点由云侧主助手生成回复，覆盖 Agent 默认话术 |
| V7 | 是否支持外部传入 POI 列表恢复上下文 | 场景 5 恢复 | 重新进入 Agent 时直接发送选择指令，由 Agent 内部重新搜索后自动匹配 |

**POC 结论判定标准**：
- V1-V4 任意一项不支持，都有云侧兜底，不阻塞方案落地
- **V5 即使不支持也不阻塞**，因为云侧前置判断已作为主方案覆盖场景 5
- V5 支持时场景 5 有双重保障；不支持时仅靠云侧前置判断同样可覆盖
- V6-V7 为体验优化项，不影响核心功能落地

## 8. 未决问题与风险

### 8.1 风险清单

| 编号 | 风险 | 影响 | 概率 | 缓解措施 |
|---|---|---|---|---|
| R1 | 高德 Agent SDK 不支持非导航意图主动回退 | 场景 5 无法优雅处理 | 中 | **主方案：云侧前置判断层拦截**，Agent 回退仅作为兜底 |
| R2 | Agent 话术与雷鸟品牌不一致 | 用户体验割裂 | 中 | 通过 Agent 配置项调整；关键节点由主助手生成回复 |
| R3 | Agent 对极端输入的处理不可预测 | 边界场景体验不可控 | 中 | 关键边界场景在云侧规则引擎前置处理 |
| R4 | 端云长连接不支持云→端下行消息 | 端云通信协议无法落地 | 低 | 与基础架构团队确认；若不支持推动长连接改造或轮询过渡 |
| R5 | Agent SDK 集成复杂度高，接入周期长 | 项目延期 | 中 | 先做 POC 验证集成可行性，再排正式开发周期 |
| R6 | 导航中控制指令延迟（多一层 Agent 转发） | 用户说"结束导航"后响应慢 | 低 | 导航控制指令由云侧直接调 stop_navigation，不经过 agent_dialog |

### 8.2 未决问题

| 编号 | 问题 | 建议推进方式 |
|---|---|---|
| Q1 | 高德 Agent SDK 是否支持非导航意图主动回退？ | 联系高德技术支持确认，或 POC 验证 V5 |
| Q2 | 是否支持 `direct_navigation` 参数？ | 同上，POC 验证 V2 |
| Q3 | Agent SDK 话术是否可配置？ | 同上 |
| Q4 | 是否支持外部传入 POI 列表恢复上下文？ | 同上，POC 验证 V7 |
| Q5 | 现有端云长连接是否已支持云→端下行消息？ | 与基础架构团队确认 |
| Q6 | Agent 持有控制权的超时时长（5 分钟是否合理）？ | 产品定义，可 A/B 测试 |
| Q7 | 眼镜端（0x20）是否需要适配导航 UI？ | 与眼镜端团队确认（当前方案假设不需要） |
